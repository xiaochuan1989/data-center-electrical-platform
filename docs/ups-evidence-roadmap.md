## 1. 目标和依据

本轮升级围绕现有 UPS 选型流程，补齐“技术条件来自哪里、工程师改了什么、输出能否追溯”的闭环。流程为：

`客户资料 → 提取候选值与原文证据 → 工程师确认/修订 → 确定性校核 → 采用型号 → 历史与导出`

两份本地资料用于方向判断，不作为 UPS 技术参数或计算依据：

- [《AI时代，工作机会正流向哪里》](../AI时代，工作机会正流向哪里｜得到AI学习圈X科锐国际.pdf)：第28页关于接入工作流，第34页关于行业经验转为判断与落地，第42页关于 FDE 对落地结果负责。
- [Datawhale《FDE案例100》](../Datawhale《FDE案例100》.pdf)：案例17（PDF第167～177页）关于结构化输入、企业规则、人工校准与反馈；案例11（PDF第107～118页）关于文件关系和企业内数据；案例23（PDF第227～233页）关于小范围验证与业务分流。该文件当前目录列出24个案例，“100”是案例集名称，并非当前文件已含100个完整案例。

当前基础包括技术条件确认、程序校核、人工采用/偏离说明、目录版本/在售状态、历史快照及 JSON 备份。新增能力复用这些入口，不重新搭建项目工作台。

## 2. 本次实施范围

本次按 S1～S4 顺序完成：

1. 技术条件逐字段保留原文片段及来源；上传资料保留文件名和可验证的位置。
2. 保留提取候选值、工程师确认值及修改原因，形成修订记录。
3. 历史快照、JSON 备份/恢复、Excel 校核表、技术说明和打印/PDF同步承载证据与修订。
4. 完成新旧数据兼容与真实业务样例验证。

PDF文本读取及扫描件识别的现有支持程度，在 S1 先核对。扫描件无可用文字时须明确要求识别或人工补录；不能把空文档判定为提取成功，也不能编造页码。

后续候选项包括标准/待补充/复杂询价分流、客户澄清清单、结果反馈指标、字段级厂家资料来源及私有报价串联。本次不把这些候选项列为交付要求，也不增加账号、后台或跨设备同步。它们需基于 S4 的试用反馈分别确定范围。

## 3. 数据设计约束（S1 已定稿）

2026-09-30链路核对：PDF.js在本机读取文字，但原逻辑拼接各页后丢失页序；DOCX由mammoth本机解析，旧DOC实际上不能由此解析；图片由外部模型OCR后填入原文。程序填入原文没有触发input事件。历史容器和JSON备份均为version=1，确认条件由normalizeUpsRequirement筛选字段，会丢弃新增证据；导出也需显式接入。

定稿：新增独立纯逻辑模块src/modules/ups-evidence.js。确认条件追加evidenceVersion=1、evidenceText、sources、fieldEvidence和revisions；来源segments保存原文字符范围及真实PDF页序，字段保存所有候选片段、范围、候选值、确认值和复核状态。修订保存每次变化（包括清空/撤销）及原因。历史容器和JSON容器继续version=1，以可选evidenceVersion扩展；项目级schema不变。旧记录继续可读，明确显示未保存证据；新记录不伪装成旧记录已具证据。

现有确认条件的顶层数值字段继续供校核函数读取。证据和修订作为附加结构保存，避免把来源信息混入计算值。

| 结构 | 建议内容 | 约束 |
|---|---|---|
| 资料来源 `sources` | 稳定ID、来源类型、文件名/用户标签、导入时间 | 只记必要元数据；不保存本机绝对路径，不默认长期保存原文件 |
| 字段证据 `fieldEvidence` | 字段键、来源ID、原文片段、页码或段落位置、提取方式、候选值、确认值、复核状态 | PDF页码从1开始，指文件页序；无页码时留空并用可验证段落/行位置 |
| 修订记录 `revisions` | 字段键、修改前值、修改后值、原因、发生时间 | 不能只存最后值；清空或撤销也需可追溯 |
| 历史快照 | 确认条件、证据、修订、规则/目录版本、人工采用结果 | 保存时复制快照，后续编辑不反向改变旧记录 |

补充规则：

- 正则提取、AI提取和人工填写使用不同来源标记；候选值与人工确认不能混为一个字段。
- 多份资料或同一资料的冲突值须保留证据并让工程师选择，不能只取第一个值而丢掉冲突。
- 确认后修改原文或技术条件必须使相关确认失效；证据不能继续指向已被替换的原文。
- 人工修改或补录技术条件时记录简短原因；正常确认无需重复填写原因。
- 首版不要求模型提供概率。若模型返回置信度，只作未经校准的辅助信息，不能替代工程师确认或触发自动放行。
- 资料缺失保持未知。证据补全本身不改变容量、冗余、电池兼容或后备时间等程序校核结论。
- 历史记录、备份容器及新增结构的版本方式在 S1 根据实际读取/恢复逻辑定稿；不预设必须改项目级 schema。
- 旧记录缺少证据时标为“历史记录未保存证据”，不推测原文、页码或修订过程。
- 现有外部 AI 调用会发送输入文字或图片；新增文档解析优先在本机执行，扩大发送内容须在界面明确呈现。
- AI辅助选型只附带既有技术条件标量，不额外发送新增来源文件名、证据元数据或人工修订原因；这些数据留在本机历史和用户主动导出的文件中。

## 4. 分阶段交付与验收

| 阶段 | 交付内容 | 完成条件 |
|---|---|---|
| S0 文档基线 | 本计划、产品/开发文档接续入口 | 范围、状态、下一步可查；不把计划写为已发布能力 |
| S1 解析与数据契约 | 核对文档上传、提取、确认、历史/备份及导出链路；定稿字段和兼容方式 | 文本、PDF、图片、人工输入各有来源/位置规则；新旧数据读写与回退方式明确 |
| S2 证据与确认界面 | 提取证据、查看来源、人工修订原因、确认失效、保存快照 | 一条真实需求从输入到采用型号可跑通；修改后需要重新确认；未知仍不放行 |
| S3 历史与交付输出 | 恢复/比较、JSON、Excel、技术说明、打印/PDF | 页面、恢复记录和输出的确认值、证据、修订、风险一致；旧备份可读 |
| S4 业务验收 | 脱敏样例回归、小范围使用记录、问题与下一批优先级 | 阶段测试和浏览器回归完成；有可复查的结果记录，再安排后续能力 |

S1主要核对 `index.html` 中的文档上传、图片识别、`extractUpsCriteria()`、`readUpsCriteria()`、`saveSelectionHistory()`、历史恢复及各导出入口；`src/modules/ups-selection.js` 的解析/归一化为纯逻辑入口。预计新增证据归一化或差异函数时使用独立模块，具体拆分在 S1 定稿。

### 验收样例

- 文本需求明确200kVA、三进三出、30分钟：证据片段正确，后备时间仍需电池曲线校核。
- 多页PDF含多个容量或相互矛盾的条款：页序及片段可复查，冲突进入人工确认。
- 扫描/图片资料或文字提取为空：提示可用处理路径，不伪造已提取字段。
- 工程师把候选值200kVA改成250kVA并说明原因：前后值、时间、原因在历史与导出一致。
- 确认后修改原文、技术条件或替换资料：确认失效，旧证据不作为新条件的已确认依据。
- 旧历史和旧JSON备份恢复：原信息保留，缺失证据如实显示，不冒充新流程记录。
- 新JSON备份往返、存储失败和导出：不丢证据，不在保存失败时显示成功。

S2/S3按改动执行相关 UPS 纯函数、历史兼容和导出检查，并做真实浏览器回归；发布前执行开发手册要求的 Node、完整 Python、公开构建审计和浏览器检查。测试结论须记录实际命令及结果，未执行项标为未验证。

### 2026-10-01 真实样例与产品范围核对

- 用户提供四份招标资料。按PDF/Word/Excel只读流程和extract-spec准备流程本机解析；DOCX识别UPS主机/电池开关箱，无修订痕迹；PDF24页；关键参数表38行6列。仅将脱敏问题摘要写入本文件，原文/项目标识/完整路径及截图不纳入版本化文档。
- 本机Chrome实际上传两份DOCX及PDF：文件读取、追加来源和24页页序正常，但跨段落的两种UPS容量和“输出功率因数为1”未进入提取结果。空容量阻止开始选型，过载分钟数未误作后备目标。
- 验收模拟人工补录两个容量子方案并说明原因：确认失效、独立快照、JSON/Excel/HTML导出正常，资料不足仍没有完全满足推荐。模拟选择不代表用户最终确认、厂家承诺或投标采用。
- 关键参数XLSX不在需求上传范围；不得通过顶部产品数据库Excel导入代替。该表的禁止偏离标记、最大并机能力不等于实际安装台数、按图/XX占位等尚未进入业务复核结构。
- 原文件SHA-256未变化，独立浏览器存储，无外部写请求及pageerror；没有调用外部AI/OCR。正式标准合规、实际型号及整份标书满足性均未宣称通过。
- 私有验收记录：`output/ups-evidence-s4/business-acceptance.md`、`sources.json`、`pure-probe.json`；浏览器材料：`output/playwright/ups-real-s4/`。这些目录被Git忽略并不进入公开构建。
